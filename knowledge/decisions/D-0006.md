# D-0006 — A sheet's identity is its cell, not its map id

Accepted 2026-09-23.

Rusty's atlas reported nine sheets and showed two regions. The atlas kept one sheet per map
id, which is what vanilla items carry, but two maps started in the same 128-block grid cell
at the same scale get different ids and identical bounds, and the atlas painted one over the
other. Nine sheets, two cells. Rusty: "maps with different IDs can cover the same regions";
"yes, fold into this release".

The accepted identity is the cell: dimension, scale and centre. A map bound at the
cartography table whose cell the atlas already charts folds: its charted pixels are copied
onto the held sheet's uncharted pixels (a pixel the atlas already charts is kept as it is),
the map is consumed, and the count does not change. A map whose id is already inside is
still refused, as before, since it would fold nothing. An atlas that already charts a cell
twice folds the moment it is held: every later sheet of a cell folds onto the cell's first
sheet, the spare maps leave the atlas, and the holder is told how many folded. Banner and
frame markers on a spare do not carry over; vanilla exposes no way to add one without the
banner standing in the world.

Rejected: keeping the spare item inside uncounted (the count would no longer describe the
container, and shears would hand back a map that charts nothing new); handing the spare
back from the table (the table consumes its inputs and has one output); folding atlases
lying in chests (nothing holds them, so nothing can tell their owner).

Only the server decides a fold. Client-side map data is built by `createForClient` and carries
no centre, so on the client every sheet looks like cell (0, 0) and the first booth run folded
the second sheet in the client's preview. The table's result takes the player's level and
folds only on a `ServerLevel`; the client predicts a plain bind and the server's slot update
corrects it a tick later in the fold case.

The fold plan is domain code (`Folding`, JUnit); the pixel copy and the item rewrite are in
`AtlasPages`; the table computes its result from the plan and merges on take. Two GameTests
cover the table and the held atlas; the booth binds a third sheet of the first sheet's cell
and the real client shows two.
